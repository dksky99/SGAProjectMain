# 프로젝트 전체 구조와 읽는 순서

## 전체 구조를 먼저 연결하기

이 프로젝트는 Unreal Engine 5.4 기반으로 로비에서 작전·임무와 장비를 선택하고, 전장에 출격해 적과 싸우며 목표를 수행한 뒤 탈출·정산하는 게임을 구성한다. 모든 게임 코드는 SGAProjectMain이라는 하나의 Runtime 모듈에 들어 있다. 캐릭터·전투·AI·임무·장비·UI·월드 오브젝트는 폴더와 클래스로 역할을 나누며, DataTable/DataAsset과 Blueprint가 종류별 설정을 공급한다.

가장 먼저 기억할 연결은 세 가지다. GameInstance는 앱을 켠 동안 맵 사이의 데이터와 현재 선택을 보관한다. GameMode는 현재 맵의 임무 진행과 종료를 관리한다. Character와 장비·AI·위젯은 이 둘의 정의와 실행 상태를 받아 실제 행동·표시를 수행한다. 디스크에 남는 것은 별도 SaveGame으로 옮겨 저장한 데이터다. 이 수명 차이를 이해하면 어디에 필드를 추가해야 하는지 판단하기 쉽다.

대표 게임 흐름은 로비 상호작용 → 글로브에서 작전/임무 선택 → PreDeploymentState에 선택 기록 → 출격 준비에서 장비 ID 선택 → OpenLevel → 전투 GameMode와 캐릭터 생성 → 캐릭터/장비 초기화 → 목표 진행/증원/탈출 → MissionResult 계산 → SaveGame 반영 → 로비 복귀다. 화면이 이동해도 유지할 정보는 GameInstance 쪽에, 전투 한 번의 진행 정보는 GameMode 쪽에, 실제 피격·조작 상태는 캐릭터와 컴포넌트에 있다.

Source의 C++/C# 파일은 헤더 포함 398개다. Content에는 테스트·템플릿·외부 리소스까지 포함해 38개 맵이 있다. 에디터 시작 맵은 LeveL_Proto3, 기본 게임 시작 맵은 FirstPersonMap으로 서로 다르다. 대표적인 로비/프로토타입/테스트 맵과 수입 리소스 데모 맵이 함께 있으므로 이름이 존재한다는 이유만으로 현재 게임에서 사용되는 맵이라고 가정하지 않는다. 근거는 Config/DefaultEngine.ini:73,80이다.

## 정의 데이터 실행 상태와 표시 데이터

정의 데이터는 무엇을 만들고 어떤 규칙으로 동작시킬지 지정한다. FGunData는 총 종류와 컴포넌트 클래스·기본 수치를, FGunProjectileData는 탄의 이동·장갑 관통·피해를, 유닛/부위/상태 데이터는 캐릭터 수치를, Mission/Operation/Objective DataAsset은 게임 목표와 제한 조건을 정의한다. DataTable의 숫자 ID와 DataAsset의 참조가 실제 Actor 클래스와 연결되는 위치를 찾는 것이 첫 단계다.

실행 상태는 이번 플레이에서 변한 값이다. 현재 HP/파괴 부위/상태 이상 지속시간/현재 자세/탄창·약실/쿨다운 마지막 사용 시간/현재 AI 타겟/분대 활성 여부/임무 남은 시간이 여기에 해당한다. 정의에서 복사한 값이라도 실행 중 바뀌면 개별 객체가 소유해야 한다. 여러 Actor가 같은 정의 DataAsset에 입력 버퍼나 위젯 포인터를 저장하면 서로의 상태가 섞일 수 있다.

표시 데이터는 실행 상태를 화면과 애니메이션이 사용할 모양으로 만든 값이다. AnimInstance의 이동 속도·방향·조준 각도·제자리 회전값, HUD의 HP/탄약/쿨다운, 결과 화면의 정산 항목이 해당한다. 일부는 Tick에서 읽고 일부는 델리게이트로 받는다. 실제 값을 바꾸는 경로와 표시를 갱신하는 경로가 함께 연결되어야 한다.

## Unreal 객체 유형을 이 프로젝트에 적용하기

Actor는 월드 위치와 BeginPlay/EndPlay 수명을 갖는 실행 객체다. 캐릭터, 총, 총알, 글로브, 단말, 포드, 센트리가 Actor다. ActorComponent는 특정 Actor의 기능과 상태를 묶는다. Stat/State/Inven/Ammo/Fire/Explosion/Stratagem 등이 해당하며 GetOwner로 소유 Actor를 찾는다.

UObject는 월드에 직접 배치하지 않는 데이터/흐름 객체에도 쓰인다. PreDeploymentState는 GameInstance를 Outer로, PreDeploymentFlow는 출격 포드를 Outer로 만들어진다. Outer는 소유 문맥을 나타내며 UPROPERTY로 참조한 객체는 Unreal GC가 추적한다. 월드 접근과 디스크 저장은 별개의 문제다. DataAsset은 편집기에 저장된 정의 객체이며, 같은 자산을 여러 소비자가 참조할 수 있다.

Widget은 데이터의 원본 소유자라기보다 표시·선택 입력의 소비자다. 다만 UIManager가 모든 화면을 통제하는 것은 아니다. PlayerCharacter가 직접 HUD를 만들고, 글로브·출격 흐름·결과 GameMode 등도 각각 위젯을 만든다. 변경할 UI가 어떤 생성자와 이벤트에 연결되어 있는지부터 확인해야 한다.

델리게이트는 상태 변화와 반응을 연결한다. 부위 HP가 0이 되면 파괴 델리게이트가 부위별 행동과 사망을 호출하고, 총의 발사 이벤트가 총 Actor의 Fire를 호출하며, 목표 완료 이벤트가 GameMode와 HUD로 전파된다. AddDynamic은 리플렉션 함수 연결이고 AddUObject/BindUObject는 C++ 객체 연결이다. 호출 빈도·대상 수명·중복 구독·해제를 실제 코드를 통해 확인해야 한다.

## 기여 범위와 변경 경계

본인 담당은 애니메이션, 캐릭터, AI, 랜드스케이프, 상태, 부위 파괴다. 팀원 담당은 장비, UI, 스트라타젬이다. 이 구분은 설명과 변경 이력을 정리하는 기준이며 실제 클래스의 의존성을 분리해 주지는 않는다. 예를 들어 총 재장전은 팀원 장비 코드가 자신의 캐릭터 상태/애니메이션에 요청하고 섹션 종료 호출을 다시 받는 기능이다. 부위 피해는 팀원 투사체가 만든 FCDamageEvent를 자신의 CharacterBase/StatComponent가 처리한다.

변경 시에는 ‘작성자’보다 ‘입력·출력 계약’을 먼저 본다. 어떤 객체가 값을 결정하는지, 어떤 객체가 복사본을 읽는지, 어느 시점에 이벤트를 보내는지, 재시작/맵 이동/풀 재사용 때 무엇이 초기화되는지를 확인한다. 각 장 마지막의 변경 영향과 읽는 순서가 이를 위한 안내다.

## 문서를 읽는 방법

처음에는 이 장에서 전체 맵을 잡은 뒤 캐릭터 계층과 입력, 상태·애니메이션, 부위 피해를 읽는다. 다음으로 AI Controller/BT와 분대·월드 흐름을 연결한다. 장비·스트라타젬 장에서는 캐릭터가 요청한 일이 실제 자원 소비와 피해로 바뀌는 과정을 읽고, 게임 진행·UI·세이브 장에서 맵 사이의 전달을 완성한다.

기억을 복구하는 두 번째 읽기는 하나의 시나리오로 진행한다. ‘총 한 발이 적의 다리에 맞는다’, ‘사망 후 증원한다’, ‘장치를 던져 센트리를 호출한다’, ‘단말 목표를 완료하고 탈출한다’를 골라 관련 장과 함수만 순서대로 읽는다. 모든 파일을 디렉터리 순서대로 읽는 것보다 호출 경계를 기억하기 쉽다.

경로는 별도 표기가 없으면 저장소의 SGAProjectMain/Source/SGAProjectMain 아래다. Config와 Content는 저장소의 SGAProjectMain 아래이며 줄번호는 2026년 10월 10일 현재 파일 기준이다. 파일이 바뀌면 줄번호보다 함수 이름으로 다시 찾는다. 설명은 구현된 동작, 비어 있는 확장 지점, 주석 처리된 이전 경로, BP에서 연결할 부분을 구분해 읽도록 구성되어 있다.

## 확인된 실행 기반

현재 작업 폴더는 UE 5.4.4 Development Editor 증분 빌드에 성공했다. 미션 데이터 1개를 대상으로 한 DataValidation 커맨드렛도 종료 코드 0으로 끝났으며 애니메이션 Blueprint 경고가 함께 기록되었다. 이는 소스/모듈/대상 에셋 로딩을 확인하는 기반이다. 개별 게임플레이 설명을 플레이 검증 완료 표시로 해석하지 않는다.

기존 오류와 개선 우선순위는 별도의 PORTFOLIO_AUDIT_2026-10-10.md에 정리되어 있다. 이 설명서에서는 동작을 이해하는 데 필요한 곳에만 현재 구현의 주의점을 붙인다. 먼저 원래 구조를 이해하고, 그다음 감사 문서의 ID별 수정 범위를 적용하면 기존 연동을 놓치지 않기 쉽다.
